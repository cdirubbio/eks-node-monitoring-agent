= Dynamic max-pods

EKS Auto Mode sizes kubelet max-pods as `min((IPv4 addresses per ENI - 1) * ENIs, 110)`
(56 on a t4g.xlarge). On nodes that receive /28 prefixes, the EKS Auto IPAM controller
(IPAMC) can back far more pods than that. With dynamic max-pods, a node's max-pods follows
the IPs IPAMC actually assigns, so CPU-bound nodes with small pods are not capped by IP
math they no longer need.

== How it works

. A NodeClass opts in with `spec.advancedNetworking.dynamicMaxPods: true`.
. Karpenter adds `dynamic-max-pods = true` to `[settings.advanced-networking]` in the node's
  user data. The agent's systemd drop-in passes `--dynamic-max-pods` only when that setting
  is true.
. IPAMC creates the node's CNINode with `spec.dynamicMaxPods: true`, warms /28s past the
  static limit, and sets `status.maxPods` to the assigned pod IP count. It is floored at the
  max-pods the node launched with and capped at 110. It is written in the same status update
  as the IPs that back it.
. The agent watches only its own CNINode (`metadata.name=<node>`) and reconciles only when
  `status.maxPods` changes. On a change it:
.. records the boot max-pods as the baseline in `--dynamic-max-pods-state-path`
   (first change only)
.. clamps the value to `[baseline, 110]`
.. persists its intent
.. runs `apiclient set settings.kubernetes.max-pods=<n>`
. The agent writes nothing back to the API. Kubelet reports the applied value as the Node's
  `status.allocatable.pods`.

Raises are rate limited by `--dynamic-max-pods-min-interval` (default 2m). Lowers and
restoring the baseline are never rate limited. A malformed `status.maxPods` is ignored.
When `status.maxPods` is unset, the agent restores the baseline.

NOTE: A `settings.kubernetes.max-pods` commit restarts kubelet only on AMIs that map it to the
`kubelet-max-pods` service; older AMIs also restart this agent. The agent persists its intent
first and, after a restart, sees the setting already applied and does nothing.

== RBAC

The agent's identity (`eks-auto:node-monitoring-agent`) needs read-only access to CNINodes:
`get`, `list` and `watch` on `cninodes` in `eks.amazonaws.com`. For production, add this
rule to `nmaRules` in EKSAccessEntryServiceLambdaPolicies. For a dev cluster:

[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: eks-auto-node-monitoring-agent-dynamic-max-pods
rules:
- apiGroups: ["eks.amazonaws.com"]
  resources: ["cninodes"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: eks-auto-node-monitoring-agent-dynamic-max-pods
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: eks-auto-node-monitoring-agent-dynamic-max-pods
subjects:
- apiGroup: rbac.authorization.k8s.io
  kind: User
  name: eks-auto:node-monitoring-agent
----

== Verifying on a node

[source,bash]
----
kubectl get cninode <node> -o wide        # MAXPODS column shows status.maxPods
kubectl get node <node> -o jsonpath='{.status.allocatable.pods}'
journalctl -u eks-node-monitoring-agent | grep -i "max pods"
cat /var/lib/eks-node-monitoring-agent/max-pods.json
----
